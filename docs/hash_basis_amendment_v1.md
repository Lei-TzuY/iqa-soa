# Hash-Basis Amendment v1

Amendment ID: `hash-basis-amendment-v1`
Applies to repository state: `47e237c339f62640ab52edc95d5bf09f22c62c36` (canonical `main`)
Machine-readable sidecar: `docs/hash_basis_amendment_v1.json`
Governing policy: `docs/hash_basis_policy.md`

**This amendment is additive. No historical frozen evidence file is edited by it.**
No experimental result, no scientific metric, and no benchmark semantic is changed.
Its sole purpose is to supply the portable canonical hash basis for artifacts whose
historical digests were recorded from a non-LF local materialization.

---

## 1. Finding

Some SHA-256 digests recorded in this repository's historical records were computed
from working-tree bytes that carried CRLF line endings, produced by Git for
Windows' default `core.autocrlf=true`. The committed blobs for those same artifacts
are, and always were, LF-only.

Such a digest is a **valid digest of a byte sequence that really existed on disk**.
It is not evidence of content modification, and it does not indicate that different
semantic data was ever frozen, observed, or analysed. The difference is confined
entirely to line-ending representation.

Of 164 digest references surveyed across the frozen records at `47e237c`, 128
resolve to the canonical LF basis and 16 references (covering 5 distinct artifacts)
resolve to a non-LF local materialization. The remainder are derived digests
(evidence fragments, run manifests) not bound to a tracked source file.

## 2. Primary subject artifact

**Artifact:** `docs/preregistration_coverage_extension_v3.md`

| property | value |
| --- | --- |
| Historical recorded working-tree SHA-256 | `d9d5f6aad993b9b106d22f06e9e9a347f74c4f5b571449f48ab512bf0c2589a1` |
| Observed bytes | 34016 |
| CRLF terminators | 518 |
| Bare LF terminators | 50 |
| EOL form | **MIXED** |
| Canonical LF / committed-blob SHA-256 | `6b7a33501f4610a73f35770314368ecc2aee4eadeab1f5f51b6e09c847409efe` |
| Canonical LF bytes | 33498 |
| Committed blob object | `git cat-file blob 47e237c:docs/preregistration_coverage_extension_v3.md` |

### Verified relations

- The historical materialization was re-observed in the original working tree and
  hashes to `d9d5f6aa…` exactly. The digest is reproducible from those bytes.
- Applying `CRLF -> LF` to those bytes yields a sequence that is **byte-for-byte
  identical** to the committed blob (33498 bytes, `6b7a3350…`). Verified by direct
  byte comparison, not by digest agreement alone.
- Therefore `d9d5f6aa…` is **not an orphan digest** and is **not evidence of
  historical content modification**. It differs from the canonical artifact only in
  line-ending representation.

### Additional observation: the mixed form is not clone-reproducible

A fresh clone of `47e237c` under `core.autocrlf=true` materializes this file with
568 CRLF and 0 bare LF, hashing to
`1a4c6ce72730d27975b18a5e9b827d8e329dff3aee6824190666e69f6841620a`.

That is a **third** value, distinct from both `d9d5f6aa…` and `6b7a3350…`. The
mixed 518/50 form recorded historically arose in one specific local working tree
and is not regenerated by any clone under any `core.autocrlf` setting. This is
stated as an observation about materialization only. The exact historical sequence
of local edits and checkouts that produced the mixed form is **not known**, and no
claim is made about it beyond what the bytes themselves prove.

This makes the practical point sharply: only the LF basis (`6b7a3350…`) is portable
and reproducible, which is why it is adopted as the canonical basis going forward.

### Archival EOL reconstruction mask

The mixed materialization is **not clone-generated**, and once the working tree is
refreshed to canonical LF it ceases to exist on disk anywhere. Its exact final byte
representation is nevertheless preserved: it is now reconstructible from the
canonical blob plus a recorded end-of-line mask.

The mask is stored in `docs/hash_basis_amendment_v1.json` under this artifact's
`historical_eol_reconstruction` key (convention `eol-mask-v1`). It records the
0-based ordinals, in canonical-LF stream order, of the LF terminators that were
represented as **bare LF**; every other LF terminator was CRLF.

Reconstruction procedure — starting from the canonical LF blob
(`6b7a3350…`, 33498 bytes, 568 LF terminators):

1. enumerate the LF terminators in stream order as ordinals `0` through `567`;
2. leave each of the 50 ordinals listed in `bare_lf_terminator_indices` as a bare
   LF (`0x0A`);
3. replace every other LF terminator with CRLF (`0x0D 0x0A`);
4. alter no other byte.

The result is 34016 bytes with 518 CRLF and 50 bare LF, and hashes to
`d9d5f6aad993b9b106d22f06e9e9a347f74c4f5b571449f48ab512bf0c2589a1`. Applying
`CRLF -> LF` to it returns the canonical blob byte-for-byte.

The mask is lossless for this artifact because the canonical blob contains no `CR`
byte at all and the historical copy contained no `CR` outside a CRLF pair. Every
line terminator is therefore either bare LF or CRLF, and nothing else differs, so
the ordinal list fully determines the original byte sequence.

As an observation about the recorded bytes: the 50 bare-LF ordinals form a single
contiguous terminal run, `518` through `567` — the first 518 terminators are CRLF
and the final 50 are bare LF.

This records **the observed final byte pattern only**. It does not reconstruct, and
makes no claim about, the sequence of edits, checkouts, or freeze mechanics that
produced that pattern.

The mask was captured from the original mixed working-tree copy while that copy
still existed, and the reconstruction was verified byte-for-byte against it at that
time. `tests/integration/test_hash_basis_invariants.py` re-verifies the
reconstruction from the committed blob alone, so the check remains valid from any
fresh canonical checkout and never depends on a stale working tree. The historical
mixed byte file itself is deliberately **not** added to Git.

## 4. Artifacts already on the canonical LF basis

Most recorded digests were already LF-basis and need no amendment. The
scientifically load-bearing example is:

| Artifact | Frozen SHA-256 | Basis |
| --- | --- | --- |
| `docs/phaseD_instrument_qualification_plan.md` | `2896f0e0263a36ab8eb240ccfbeb2ace35057cec16e3f0fe943ed13adf5fcc2a` | canonical LF |

This digest is enforced at runtime by the Phase-D verifier's plan-boundary check.
Under a CRLF checkout the same file hashes to `bd6ce851…` and the check fails. This
is the failure mode the checkout policy repairs; the frozen digest itself was
correct throughout.

Every frozen `case_sha256` entry in every `benchmark/pilot-*/manifest.json` is
likewise already on the LF basis, which is why frozen-case validation passes in a
canonical checkout.

## 5. Statements of record

1. `d9d5f6aa…` was a valid digest of an actual local working-tree byte sequence.
2. It does **not** represent different semantic or content data.
3. `CRLF -> LF` applied to those bytes produces bytes identical to the committed
   artifact — verified by byte comparison, not by digest agreement alone.
4. The original historical records remain **unchanged**; no historical digest has
   been overwritten, silently or otherwise.
5. This amendment supplies the portable canonical hash basis for future
   reproducibility checks.
6. No experimental result, scientific evidence, metric, or benchmark semantic is
   changed by this amendment.
7. No claim is made about the exact historical freeze mechanics beyond what the
   byte evidence proves.

## 6. Forward rule

New freezes MUST be generated and validated only in a checkout that satisfies
`docs/hash_basis_policy.md` §6, and MUST therefore record canonical LF digests.
Where a future check needs to validate one of the artifacts in §2 or §3, it MUST
use the canonical LF digest from this amendment, and MUST NOT rewrite the
historical record in place.
